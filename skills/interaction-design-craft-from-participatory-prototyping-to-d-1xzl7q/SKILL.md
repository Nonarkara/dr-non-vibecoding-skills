## Core principles

- Participatory design means working side‑by‑side with future users to uncover real needs and test ideas quickly.
- Prototyping is a way of thinking: build the smallest thing that lets you observe behavior and learn what to change.
- Spatial and iconic metaphors (e.g., folders, desktops) let users recognize actions instead of recalling commands.
- Reducing modes—through double‑click, cursor‑between‑characters, or modeless editing—lowers error and learning time.
- Constraints such as cost, hardware limits, or simplicity goals force designers to invent clearer, more usable solutions.
- Successful interaction patterns emerge from tight designer‑engineer loops where prototypes are built at night and tested by day.
- Menu bars placed at the screen edge give a stable, always‑visible target that users can reach without visual search.
- A browser‑style pane layout (lists + detail view) makes complex data navigable without modal dialogs.
- Cut, copy, and paste become intuitive when they operate on a visible selection and a shared buffer.
- Design evolves by borrowing metaphors from familiar worlds (offices, libraries) and then refining them through real‑world use.

# Glossary

| Term | Definition | Chapter |
| --- | --- | --- |
| **Participatory design** | Designing with future users by observing them, involving them in decisions, and iterating based on their feedback. | ch01 |
| **Usability test** | Watching real people attempt to use a prototype to discover where they struggle or succeed. | ch01 |
| **Iconic naming** | Using pictures that resemble real‑world objects to represent commands or files so users can recognize them at a glance. | ch02 |
| **Spatial metaphor** | Mapping interface elements onto familiar layouts like desks, filing cabinets, or rooms to leverage existing knowledge. | ch02 |
| **Modeless editor** | An editing mode where the same actions (e.g., typing, pointing) always have the same effect, eliminating mode‑switch errors. | ch03 |
| **Double‑click** | Two rapid mouse clicks in the same spot used to select a word (or three clicks for a sentence) without extra modifier keys. | ch04 |
| **Cut and paste** | A pair of commands that remove selected content to a buffer and then insert that buffer at the cursor location. | ch04 |
| **Cursor between characters** | Placing the insertion point in the gap between characters so typing adds new text after the left character, making the result obvious. | ch04 |
| **Smalltalk browser** | A three‑pane interface (classes, methods, code) with independent scroll bars that lets users browse and edit hierarchically. | ch05 |
| **Pull‑down menu** | A menu that remains hidden until the mouse selects its title, then appears vertically beneath it. | ch06 |
| **Menu bar** | A persistent horizontal strip, usually at the top of the screen, that holds the titles of pull‑down menus. | ch06 |
| **Affordance** | A perceivable property of an object that suggests how it can be used, such as a button’s shape indicating it can be pressed. | ch10 |
| **Feedback** | Immediate, perceptible response from the system that confirms an action has been recognized and executed. | ch10 |
| **Constraint‑driven design** | Using limits such as cost, hardware capability, or simplicity goals to focus design decisions on what truly matters to users. | ch07 |
| **Prototype‑test cycle** | A rapid loop where a builder creates a testable artifact by night and an evaluator observes real users with it by day, then feeds back observations. | ch08 |
| **Kinesthetic memory** | The unconscious ability to reach for a screen location (like a menu bar) without looking, built through repeated use. | ch06 |
| **WYSIWYG** | What You See Is What You Get—the principle that on‑screen appearance should match printed output. | ch07 |
| **Modal vs modeless** | Modal interfaces require users to be in a specific mode for actions to work; modeless interfaces keep actions consistent across contexts. | ch03 |
| **Desktop metaphor** | The concept of treating the computer screen as a virtual desk with folders, documents, and a trash can that users can manipulate directly. | ch10 |
| **Mouse button chording** | Using combinations of mouse button presses (e.g., double‑click) to issue different commands without adding physical buttons. | ch10 |

## Observe then co‑create with users

**When to use:** When starting a new interaction design and you lack clear user goals.

**Recipe:**

1. Find a small group of representative users who will actually use the system.
2. Ask them to show you how they currently achieve the goal, noting pain points.
3. Invite them to sketch or describe a better way, then build a quick prototype of that idea.
4. Test the prototype with the same users, observe where they hesitate or err, and refine.

**Chapter:** ch01

---

## Blank screen experiment

**When to use:** When you need to discover the most natural way users would manipulate an object with a new input device.

**Recipe:**

1. Give the user a blank screen and only the input device (e.g., mouse, stylus).
2. Present a simple task (e.g., delete a word, insert a sentence) using a paper reference.
3. Ask the user to describe aloud what they would do with the device.
4. Transcribe their description into concrete interaction rules (e.g., point‑then‑type for insert).

**Chapter:** ch03

---

## Iconic spatial metaphor

**When to use:** When you need to represent files, commands, or concepts that users must recognize quickly.

**Recipe:**

1. Identify a real‑world object that users already associate with the concept (e.g., folder for documents).
2. Sketch a simple, recognizable silhouette of that object, avoiding unnecessary detail.
3. Test the icon with users: can they name its meaning without explanation?
4. Iterate until the icon is instantly recognizable, then use it consistently.

**Chapter:** ch02

---

## Reduce modes via double‑click

**When to use:** When a multi‑button input device causes frequent mode errors or you want to keep the device simple.

**Recipe:**

1. Map a single click to a primary action (e.g., place cursor or select).
2. Map a rapid double‑click in the same spot to a secondary action (e.g., select word).
3. Optionally map a triple‑click to a tertiary action (e.g., select sentence).
4. Test with novices and experts to ensure the timing feels natural and does not cause accidental triggers.

**Chapter:** ch04

---

## Cut/paste buffer model

**When to use:** When you need to let users move or duplicate content within a document.

**Recipe:**

1. Define a selection mechanism (click‑drag, double‑click, etc.) that highlights the target.
2. Provide a ‘cut’ command that removes the selection and stores it in a temporary buffer.
3. Provide a ‘paste’ command that inserts the buffer contents at the current cursor position.
4. Optionally add a ‘copy’ command that leaves the original intact while storing to buffer.

**Chapter:** ch04

---

## Cursor between characters for insertion

**When to use:** When users find it unclear where new text will appear after clicking.

**Recipe:**

1. Render the insertion point as a thin vertical line (or blinking caret) positioned between two characters.
2. Ensure that clicking anywhere on a character positions the cursor either before or after it based on horizontal click location.
3. Make the cursor blink or change shape to draw attention to the active insertion point.
4. Verify that typing inserts text visibly after the left character, matching user expectation.

**Chapter:** ch04

---

## Three‑pane browser

**When to use:** When users need to navigate a hierarchy (classes→methods→code, folders→files→contents) and edit the leaf item.

**Recipe:**

1. Create three side‑by‑side panes: top‑left for the first level list (e.g., classes), top‑right for the second level list (e.g., methods), bottom for the detail view (e.g., source code).
2. Give each pane its own independent scroll bar so users can browse before committing.
3. Make the detail view editable using the same edit commands used elsewhere in the system.
4. Highlight the selected item in each list to keep context clear.

**Chapter:** ch05

---

## Persistent top‑edge menu bar

**When to use:** When you want commands to be always reachable without memorizing deep hierarchies.

**Recipe:**

1. Place a horizontal strip at the very top of the screen, spanning the full width.
2. Distribute menu titles evenly within the strip; clicking a title shows its pull‑down menu beneath it.
3. Make the menu bar a constant visual target: users only need to get the horizontal position right; vertical position can be anywhere at or above the top edge.
4. Provide keyboard shortcuts and visual highlighting for the active menu to speed up expert use.

**Chapter:** ch06

---

## Constraint‑first ideation

**When to use:** When faced with limits on budget, hardware, or time that seem to block innovation.

**Recipe:**

1. Write down the concrete constraints (e.g., max cost, CPU speed, memory, desired price point).
2. Ask: ‘What is the simplest interaction that satisfies the user goal within these limits?’
3. Brainstorm solutions that explicitly use the constraint as a feature (e.g., a white background to enable WYSIWYG despite power concerns).
4. Prototype the most promising constraint‑driven idea and test it with users to confirm it feels better, not just cheaper.

**Chapter:** ch07

---

## Designer‑engineer day‑night loop

**When to use:** When you need to explore many interaction ideas quickly and validate them with real users.

**Recipe:**

1. Pair a builder (who can code prototypes fast) with an evaluator (who can run user tests).
2. At night, the builder creates a testable artifact of one interaction idea.
3. During the day, the evaluator runs the artifact with novice users, notes where they succeed or struggle, and gives a concise debrief.
4. The next night, the builder revises the artifact based on the debrief, then starts the next cycle.

**Chapter:** ch08

## Cheatsheet

# Cheatsheet

Imperative decision rules from the source, grouped by category. Each is the kind of sentence you would write on an index card.

## general

- If users look confused, watch them first before adding more features.

## design

- When a concept is hard to explain, draw a picture of a real‑world object that resembles it.
- Prefer one button with smart clicks over many buttons that cause mode errors.
- Make the insertion point obvious: show a blinking line between characters, not on them.
- Use selection → cut → paste as the universal way to move or duplicate anything.
- When navigating hierarchies, show lists side by side with independent scroll bars.
- Put the most‑used commands in a permanent strip at the screen edge so users can reach them without looking.
- Ask: What is the best interaction for this whole thing, starting from scratch rather than copying?
- Give every interactive element an affordance that signals how to use it (shape, motion, sound).
- Provide immediate feedback for every action so users know the system heard them.
- If a menu hierarchy feels deep, flatten it by moving titles to a persistent bar.
- Use double‑click (or triple‑click) to add power without adding physical buttons.
- When users reach for a screen spot repeatedly, make that spot a stable target (e.g., menu bar top edge).
- Keep the language of commands consistent across contexts to reduce mode confusion.

## process

- Build the smallest thing that lets a user complete a core task, then test it.
- Let constraints like cost or simplicity guide you to clearer solutions, not excuse poor ones.
- Pair a programmer who can prototype at night with a tester who can watch users by day.
- Test ideas with real people as early as possible; their actions reveal the true design.
- If a prototype feels heavy, strip it down until the core interaction shines through.
