# Health

> A codebase has a quality. The quality can be measured, scored, and tracked. The score is the answer to "how good is this code" and the trend is the answer to "is it getting better."

Most engineering practices treat code quality as a feeling: "this is good" or "this needs work." The feeling is right sometimes, wrong sometimes, and never repeatable. A score is repeatable. A trend is the evidence that the team is paying attention. A score without a trend is a snapshot; a trend without a score is a guess. The health skill produces both.

The score is a **weighted composite**. It is not a single number from a single tool; it is a roll-up of independent signals, each with a weight, each contributing to a 0-10. The signals are the tools the project already uses — type checker, linter, test runner, dead-code detector, shell linter — wired into one command, scored, and tracked.

The score is the **input to the canary and to the CSO**. A codebase that is 6.2 today and 6.1 tomorrow is not drifting; a codebase that is 6.2 today and 4.8 next month is. The trend is the trigger for the [`canary`](../canary/SKILL.md) (the deploy that drops the score 1.0 in a day is the deploy that needs an investigation) and for the [`cso`](../cso/SKILL.md) (a codebase that cannot climb above 5.0 has a structural problem the audit will surface).

## The signals

The health skill wraps the tools the project already has. The signals are not invented here; they are the standard set. The weights are not invented here either; the weights are the default that the practice has tested. A project that has a different mix (more tests, no shell scripts) re-weights; a project with a different language swaps the tools but not the structure.

| Signal | What it measures | Default weight | Default tool |
|---|---|---|---|
| **Type** | The code expresses its types; the type checker passes with no `any`, no `// @ts-ignore`, no untyped exports. | 2.0 | `tsc --noEmit` (TS) · `mypy` (Python) · `go vet` (Go) |
| **Lint** | The code follows the project's style and avoids the patterns the linter flags. | 1.0 | `eslint` · `ruff` · `golangci-lint` |
| **Test** | The test suite passes; the coverage is above the project's threshold; the tests are not skipped. | 3.0 | `npm test` · `pytest` · `go test` |
| **Dead code** | Unused exports, unreachable branches, files not imported. The codebase does not carry weight it does not use. | 1.0 | `knip` · `vulture` · `deadcode` |
| **Shell** | The shell scripts in the repo (deploy, setup, CI helpers) pass the shell linter; no `set -e` violations, no unquoted variables. | 1.0 | `shellcheck` |
| **Complexity** (optional) | Functions do not exceed a cyclomatic complexity threshold. | 0.5 | `lizard` · `radon cc` |
| **Dependency freshness** (optional) | Dependencies are not pinned to versions with known CVEs. | 0.5 | `npm audit` · `pip-audit` · `govulncheck` |

The default weights sum to 8.0 (or 9.0 with the optional signals). The score is normalised to 0-10 by the weighted sum / total weight × 10. A codebase that passes every signal at the strictest level scores 10. A codebase that fails every signal scores 0. A real codebase is between.

The weights are **the practice's defaults**, not the project's defaults. A project that cares more about tests than about types re-weights to 4.0 for tests and 1.0 for types. The health skill reads the weights from `.health/config.yaml`; the file is one block of YAML, generated by `setup.sh` on first run, editable by the team.

## The score, the band, the trend

Three outputs from one run.

### The score — a single number, 0-10, with per-signal breakdown

The score is the answer to "how good is this code, right now." A run that finds `7.4` means: weighted average across the seven signals, 7.4 out of 10. The breakdown shows the per-signal score (e.g., types 9.2, lint 7.0, tests 6.5, dead-code 8.0, shell 9.0) so the team can see *which* signals are pulling the score down. A 7.4 with all signals at 7+ is a healthy codebase that is uniformly mediocre; a 7.4 with one signal at 3 is a healthy codebase with one bad area to fix.

The score is **a 0-10 float, not a percentage, not a letter grade**. The 0-10 is the form the rest of the practice uses ([`karpathy-guidelines`](../karpathy-guidelines/SKILL.md), [`axiom-design-core`](../axiom-design-core/SKILL.md)), and it is the form the trend tracks.

### The band — green / yellow / red with a default threshold

The band is the answer to "is this codebase healthy enough to ship?" The default thresholds:

| Band | Score | Meaning |
|---|---|---|
| **Green** | ≥ 8.0 | Healthy. Ship without comment. |
| **Yellow** | 6.0 – 7.9 | Functional. Ship with a note. The next sprint should improve the lowest signal. |
| **Red** | < 6.0 | Unhealthy. Do not ship a major change without an explicit score-improvement plan. |

The thresholds are editable in `.health/config.yaml`. A team that is comfortable shipping at 6.5 raises the red threshold; a team that is strict about quality lowers the green. The band is the operator's call, not the tool's.

### The trend — the score over the last N runs

The trend is the answer to "is it getting better." The trend log is a single-column file at `.health/trend.jsonl`: one JSON object per run, with the date, the commit, the score, the band, the per-signal breakdown. The last 30 runs are the trend; the last 90 are the trajectory.

The trend is **the only output that survives a bad run**. A red run today, with a trend of green-green-yellow-yellow-red, is a codebase that drifted over a month — the diagnosis is "slow decay, not single event." A red run today, with a trend of green-green-green-red, is a codebase that broke today — the diagnosis is "find the change that caused it." The trend is the input to the diagnosis; the score alone is not.

## The protocol

A health run is three commands. The first captures the baseline (run on first invocation), the second scores, the third appends to the trend.

### 1. Bootstrap — first run only

`scripts/health.sh --init` reads the project's package manager / build tool, detects the available signals, writes `.health/config.yaml` with the detected tools and the default weights, and runs the first scoring. The bootstrap is one-shot; the file is committed and never auto-edited again.

### 2. Score — every run

`scripts/health.sh` runs the configured signals, computes the weighted score, prints the band, and (unless `--no-log`) appends to `.health/trend.jsonl`. The script is fast (sub-second on a warm cache for most projects), safe to run on every commit, and cheap enough to run on every CI job.

The score is **deterministic for a given commit**. Two runs on the same commit, in the same repo state, produce the same score. Determinism is the property that makes the trend meaningful; without it, the trend is noise.

### 3. Read — when someone asks

`scripts/health.sh --read` prints the last 30 trend rows, the current score, the band, and a one-line per-signal breakdown. The read is the input to a code review, a planning meeting, a [`cso`](../cso/SKILL.md) audit, or a [`power-of-hindsight`](../power-of-hindsight/SKILL.md) reconstruction. The read is the question "how good is this code, right now, and is the answer getting better or worse."

## What the score is *not*

**It is not a measure of correctness.** A codebase can score 10 and still have a bug; a codebase can score 4 and still ship a working product. The score measures *quality*, not *correctness*. The [`browser-as-t`](../browser-as-t/SKILL.md) and [`human-walkthrough`](../human-walkthrough/SKILL.md) skills measure correctness; the [`karpathy-guidelines`](../karpathy-guidelines/SKILL.md) skill is the discipline that aims for both.

**It is not a measure of value.** A 6.0 codebase that ships a critical feature is more valuable than a 9.5 codebase that nobody uses. The score is the cost of future change, not the value of the current product. A high score on a low-value codebase is a vanity number; a low score on a high-value codebase is a real cost, and the cost is in the next change, not the current release.

**It is not a gate.** A red band does not block a deploy. The score is a measurement; a measurement is not a gate. The deploy is gated by [`deploy-verification`](../deploy-verification/SKILL.md) (the bytes are there) and [`canary`](../canary/SKILL.md) (the bytes behave). The health score is the input to the *next* improvement sprint, not the *current* deploy.

**It is not a substitute for review.** The score is what the tools can see. The [`adversarial-review`](../adversarial-review/SKILL.md) skill is what a human reviewer can see — and the human reviewer can see things the tools cannot. The score and the review are complementary; the score is the quick check, the review is the deep one.

## The pair

| This skill | Pairs with | Why |
|---|---|---|
| The score | [`karpathy-guidelines`](../karpathy-guidelines/SKILL.md) | The coding discipline aims for both quality and correctness. The score measures the quality side; the review measures the correctness side. |
| The trend | [`power-of-hindsight`](../power-of-hindsight/SKILL.md) | The trend log is one of the longitudinal data sources the hindsight skill analyses. A drift in the score is a finding. |
| The band | [`canary`](../canary/SKILL.md) | A canary that drops the score 1.0 in a day is the deploy that needs an investigation. The score is the canary's input. |
| The bootstrap | [`full-stack-bootstrap`](../full-stack-bootstrap/SKILL.md) | The bootstrap is run on the first project setup; the health init runs the same day, with the same tool detection. |
| The signal selection | [`appsec-stack`](../appsec-stack/SKILL.md) | The AppSec layer 3 (SCA) overlaps with the dependency-freshness signal. A team that uses both has consistent data; a team that uses one has a partial view. |
| The configuration file | `.health/config.yaml` | The file is a project artefact; it is committed, it is reviewed, and it is the team's stated standard for "what is good code." |

## The check

```
□ .health/config.yaml exists, committed, and edited by the team (not by the tool)
□ The score is deterministic: two runs on the same commit produce the same number
□ The trend log has at least 10 prior runs (so the trend is meaningful, not a single point)
□ The team has named the band thresholds (green ≥ 8.0, red < 6.0 by default, editable)
□ The score is on the readme or a dashboard, not buried in CI logs
□ A drop in the trend triggers an investigation, not a "we'll see"
□ The score is one input to the canary, not a gate on the deploy
```

Pairs with [`karpathy-guidelines`](../karpathy-guidelines/SKILL.md) (the discipline that aims for both quality and correctness), [`power-of-hindsight`](../power-of-hindsight/SKILL.md) (the longitudinal analysis that reads the trend), [`canary`](../canary/SKILL.md) (the deploy watch that catches single-event drops), and [`adversarial-review`](../adversarial-review/SKILL.md) (the human review that catches what the score cannot).
