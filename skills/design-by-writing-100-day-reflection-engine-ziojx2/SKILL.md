## Core principles

- Writing forces you to make invisible thoughts visible, turning vague intuition into concrete material you can iterate on.
- Begin every design effort with the most vivid, single user‑centric story you can recall without consulting notes.
- Reflection after each work session creates a cheap, high‑impact feedback loop that surfaces hidden assumptions.
- Physical activity (e.g., biking) can be used as a deliberate focus‑shifting ritual to surface new ideas and reduce mental fatigue.
- Avoid treating users as possessions; instead practice non‑possessive empathy that respects their autonomy and context.
- Incremental, low‑fidelity prototypes are safer than big‑bang redesigns because they expose failure early and cheaply.
- Tradition is a hypothesis, not a rule; test it against current user needs before letting it dictate design decisions.

## Start with a Single Vivid User Story

**When to use:** When beginning any design project or sprint.

**Recipe:**

1. Recall the most striking moment you observed with a user.
2. Write it down in one paragraph without consulting notes.
3. Extract the core need, pain point, and emotion from that story.
4. Use the extracted elements as the anchor for all subsequent work.

**Chapter:** ch02

## Incubation Bike Break

**When to use:** After a dense brainstorming or prototype session.

**Recipe:**

1. Leave the workspace for a 10‑minute bike ride or walk.
2. Maintain a light, rhythmic pace; avoid thinking about the problem.
3. When you stop, note any new ideas that surface spontaneously.
4. Add those ideas to the project backlog for later evaluation.

**Chapter:** ch04

---

## 15‑Minute Reflection Retrospective

**When to use:** End of each workday or sprint.

**Recipe:**

1. Set a timer for 15 minutes.
2. Review what you wrote or designed today.
3. Answer three questions: What worked? What surprised me? What assumptions did I make?
4. Record the answers in a journal for future reference.

**Chapter:** ch03

---

## Tradition‑Audit Checklist

**When to use:** When a standard practice feels forced or outdated.

**Recipe:**

1. List the practice you are about to use.
2. Ask: Which current user need does this satisfy?
3. If the answer is weak, prototype an alternative that addresses the need directly.
4. Test the alternative with real users before adopting it.

**Chapter:** ch05

---

## Non‑Possessive Empathy Interview

**When to use:** User research interviews.

**Recipe:**

1. Begin with open‑ended prompts, avoiding any mention of a solution.
2. Listen without interrupting; note only observations, not judgments.
3. After the interview, separate observations from inferred needs.
4. Validate each inferred need with at least two additional users.

**Chapter:** ch06

---

## Tunnel‑Vision Countermeasure

**When to use:** When deep work makes you feel stuck or blind to risks.

**Recipe:**

1. After each focused session, list three things you ignored.
2. Spend one minute exploring each listed item.
3. Add any discovered risks or opportunities to the project board.
4. Schedule a quick check‑in to address the new items.

**Chapter:** ch07

---

## Incremental A/B Hypothesis

**When to use:** When considering a design change.

**Recipe:**

1. Identify the smallest possible tweak that could affect a key metric.
2. Formulate a clear hypothesis: "If we change X, metric Y will improve."
3. Run an A/B test with a limited audience.
4. Analyze results; if positive, iterate; if negative, revert and learn.

**Chapter:** ch08

---

## Daily Design Discipline Loop

**When to use:** For long‑term design practice.

**Recipe:**

1. Write a 10‑minute user insight in the morning.
2. Take a 5‑minute movement break mid‑day.
3. Reflect for 5 minutes on what you learned.
4. Define one small experiment to run tomorrow.

**Chapter:** ch09

---

## Stream‑of‑Consciousness Ideation

**When to use:** When you need a burst of raw ideas.

**Recipe:**

1. Set a timer for 7 minutes.
2. Write continuously about the problem without editing.
3. After time is up, highlight recurring themes or pain points.
4. Turn highlighted items into actionable design hypotheses.

**Chapter:** ch02

## Cheatsheet

# Cheatsheet

Imperative decision rules from the source, grouped by category. Each is the kind of sentence you would write on an index card.

## design

- If you can't articulate a problem, write a story about the user first.
- Treat every tradition as a hypothesis, not a rule.
- Never ask a user what they need; listen to what they do.
- When a user feels possessed, step back and observe without judgment.
- Never start a design sprint without a single vivid user story.
- Write the problem, not the solution, to avoid bias.
- If you feel a design is "traditional," ask what current need it serves.

## process

- When you feel stuck, get on a bike for ten minutes.
- Always end a work session with a five‑minute reflection.
- After deep focus, list three things you ignored and explore them.
- Use a tunnel metaphor to visualize hidden risks before committing.
- If you notice you are "closing‑in," deliberately widen your focus for a minute.

## product

- Make the smallest possible change before committing to a big redesign.
- If a metric doesn't move, the hypothesis is wrong—pivot quickly.
- When a solution feels too perfect, test it with real users before scaling.

## code

- Write before you prototype; the writing becomes your low‑fidelity prototype.

## life

- Schedule a daily 10‑minute insight journal to keep ideas fresh.
- If a habit feels boring, pair it with a physical activity to refresh the mind.

## writing

- If you can't find a clear answer, write a stream of consciousness and mine it later.
- When ideas flood, capture them in a quick stream‑of‑consciousness note.
