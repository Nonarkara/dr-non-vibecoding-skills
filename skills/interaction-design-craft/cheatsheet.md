# Cheatsheet

Imperative decision rules from the source, grouped by category. Each is the kind of sentence you would write on an index card.

## general

- If users look confused, watch them first before adding more features.

## design

- When a concept is hard to explain, draw a picture of a real‑world object that resembles it.
- Prefer one button with smart clicks over many buttons that cause mode errors.
- Make the insertion point obvious: show a blinking line between characters, not on them.
- Use selection → cut → paste as the universal way to move or duplicate anything.
- When navigating hierarchies, show lists side by side with independent scroll bars.
- Put the most‑used commands in a permanent strip at the screen edge so users can reach them without looking.
- Ask: What is the best interaction for this whole thing, starting from scratch rather than copying?
- Give every interactive element an affordance that signals how to use it (shape, motion, sound).
- Provide immediate feedback for every action so users know the system heard them.
- If a menu hierarchy feels deep, flatten it by moving titles to a persistent bar.
- Use double‑click (or triple‑click) to add power without adding physical buttons.
- When users reach for a screen spot repeatedly, make that spot a stable target (e.g., menu bar top edge).
- Keep the language of commands consistent across contexts to reduce mode confusion.

## process

- Build the smallest thing that lets a user complete a core task, then test it.
- Let constraints like cost or simplicity guide you to clearer solutions, not excuse poor ones.
- Pair a programmer who can prototype at night with a tester who can watch users by day.
- Test ideas with real people as early as possible; their actions reveal the true design.
- If a prototype feels heavy, strip it down until the core interaction shines through.
